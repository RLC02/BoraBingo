Cookies e Autenticação
ATENÇÃO — token também no body

✅ O que está correto

  • ResponseCookie com httpOnly(true)
  • sameSite("Lax") configurado
  • maxAge(86400) = 24h de expiração
  • path("/") — escopo global
  • Logout apaga o cookie com maxAge(0)
  • Gateway lê o token exclusivamente do cookie primeiro
  • withCredentials: true no frontend (Axios)
  • CORS com allowCredentials(true)

⚠️ Ponto de atenção

  • O endpoint /login retorna o token também no body JSON
  • O frontend não armazena em localStorage, apenas usa o cookie
  • secure(false) — correto para localhost; em produção deve ser true
  • Fallback Authorization: Bearer no Gateway — necessário para K6
Para a apresentação: Mostre no DevTools → Application → Cookies o cookie bingo_auth_token. Confirme que nada aparece em localStorage.
// AuthController.java — login() ResponseCookie cookie = ResponseCookie.from("bingo_auth_token", token) .httpOnly(true) .secure(false) // false em dev, true em produção HTTPS .path("/") .maxAge(86400) // 24 horas .sameSite("Lax") .build(); response.addHeader(HttpHeaders.SET_COOKIE, cookie.toString());

Transações com MongoDB
ATENDIDO

ReplicaSet configurado

Todos os serviços apontam para mongodb://localhost:27017/bingo_db?replicaSet=rs0. O docker-compose.yml inicia o rs.initiate() automaticamente.

MongoTransactionManager

Bean declarado em SecurityConfig, RabbitAndMongoConfig e CartelaRabbitAndMongoConfig. Habilita o suporte a @Transactional.

@Transactional nos serviços

Aplicado em: UserService.register(), SalaService.criarSala(), SalaService.iniciarJogo(), SalaService.sortearProximoNumero(), CartelaService.processarCompraFila().

Rollback automático: O processarCompraFila() usa bloco try/catch — em caso de falha, chama rejeitarCartela() marcando status como REJEITADO, garantindo que nenhuma cartela fique em estado inconsistente.

Controle de Status das Mensagens
ATENDIDO

Ciclo de vida — StatusCompra (Cartela)

PENDENTE
← solicitarCompraCartela() — nunca nulo
PROCESSANDO
← processarCompraFila() — consumer ativo
CONFIRMADO
← validações OK + matriz gerada
REJEITADO
← rejeitarCartela() + motivo gravado

Ciclo de vida — StatusSala (Sala)

CRIADA
← criarSala() — status inicial
EM_ANDAMENTO
← iniciarJogo() — só se CRIADA
FINALIZADA
← finalizarBingo() + vencedor
CANCELADA
← enum disponível (não implementado via API)
Sem status nulo: A primeira linha do solicitarCompraCartela() é .status(StatusCompra.PENDENTE) — obrigatório no builder. A transição é sempre explícita; em caso de exceção, o catch garante que a cartela vai para REJEITADO com motivo registrado.

Testes de Carga e Concorrência com K6
ATENDIDO

Configuração do script

  • 30 usuários simultâneos disputando 20 vagas
  • Executor: shared-iterations
  • Polling no GET /api/cartelas/{id} até status final
  • Timeout: 25 tentativas × 0.4s = 10s por usuário
  • Métricas customizadas: confirmadas, rejeitadas, timeouts, erros

O que o teardown valida

  • GET /api/salas/{id} consulta cartelasVendidas
  • Confirma que não ultrapassou maxCartelas
  • Imprime relatório no console: confirmadas vs rejeitadas vs timeout
  • Saída de erro crítico se houver overbooking
## Como executar o teste de concorrência # Pré-requisito: k6 instalado (brew install k6) # Execução simples (cria sala automaticamente via setup) k6 run k6-test-concorrencia.js # Execução com parâmetros customizados k6 run -e MAX_CARTELAS=10 -e QTD_REQUISICOES=25 k6-test-concorrencia.js # Resultado esperado na tela: # bingo_cartelas_confirmadas: 20 (= maxCartelas) # bingo_cartelas_rejeitadas: 10 (= 30 - 20) # bingo_timeout_polling: 0
Concorrência de escrita: O script bypassa o Gateway (aponta direto para :8082 e :8083) e usa headers X-Auth-* diretamente. Isso simula a carga interna real. A proteção contra overbooking é garantida pela fila RabbitMQ + @Transactional no consumer.

Organização e Arquitetura do Projeto
ATENDIDO

Estrutura por módulo

  • auth-service — config, controller, dto, model, repository, service
  • bingo-sala-service — config, controller, dto, model, repository, service
  • cartela-service — config, consumer, controller, dto, model, repository, service
  • gateway-service — config (CORS), filter (AuthFilter)
  • frontend — App.js + src/services/api.js

Responsabilidades definidas

  • Controllers — HTTP, validação de entrada
  • Services — lógica de negócio, @Transactional
  • Repositories — acesso ao MongoDB (Spring Data)
  • DTOs — contratos de entrada/saída (sem expor entidades)
  • Models — entidades MongoDB (com @Document)
  • Consumer — só no cartela-service (consome RabbitMQ)
  • Config — Rabbit, Mongo, Security, CORS separados
Sem duplicação problemática: Cada serviço tem suas próprias entidades e DTOs. A comunicação entre serviços é feita via mensagem (RabbitMQ) ou REST interno (RestTemplate), não por objetos compartilhados.

Demonstração do Frontend
FLUXOS COMPLETOS

Fluxo do Usuário Comum (ROLE_USER)

  1. Cadastro via aba Cadastrar (ROLE_USER)
  2. Login → cookie bingo_auth_token gravado
  3. Listagem de salas disponíveis
  4. Entrar em uma sala com status CRIADA
  5. Comprar cartela (async) → polling → CONFIRMADA
  6. Marcar números conforme sorteio
  7. Bater Bingo → validação automática via API
  8. Logout → cookie apagado

Fluxo do Administrador (ROLE_ADMIN)

  1. Cadastro com role: ROLE_ADMIN
  2. Login → mesmo fluxo de cookie
  3. Painel admin visível: criar sala, nome, preço, max cartelas
  4. Criar sala → aparece na lista com status CRIADA
  5. Iniciar Jogo → status → EM_ANDAMENTO
  6. Sortear Número → a cada clique sorteia 1 número (1–75)
  7. Visualiza números sorteados em tempo real
Persistência de sessão: Ao recarregar a página, o App.js chama GET /api/auth/me via checkSession() — se o cookie ainda for válido, o usuário é recuperado automaticamente sem necessidade de novo login.
  • Login/logout com cookie HttpOnly — sem localStorage
  • Sessão persistente via cookie + /auth/me
  • Botões admin ocultos para ROLE_USER (UI)
  • 403 Forbidden retornado pelo backend para acesso não autorizado
  • Polling assíncrono de status de cartela (PENDENTE → CONFIRMADO/REJEITADO)
  • Integração completa com todas as APIs via Axios + withCredentials
  • Frontend React Native Web (não mobile nativo) — rode com npm start no navegador
